    Part 5: Software engineering and parallel computing

    Concept primer

    Software engineering research asks how to build and maintain large systems reliably, and increasingly how AI can help. Expect conceptual questions with a small calculation or code snippet.

    Process and quality. Development processes (waterfall, agile, continuous delivery) differ in how much they plan upfront versus learn from feedback. Testing is the main way to find defects: unit tests check small pieces, integration tests check how pieces work together, system tests check the whole. Coverage measures how much code tests execute but not whether they check the right things; mutation testing (inject small bugs and see whether tests catch them) is a stronger check. Static analysis and code review find problems without running code. Design principles (modularity, low coupling, high cohesion, SOLID) keep change cheap.

    Parallel computing. Parallel programs run on multiple cores, machines or GPUs. The limits are Amdahl's law (the serial part caps speedup) and overheads (communication, synchronization, load imbalance). The hazards are data races, deadlocks and subtle memory-ordering effects. Choose the model by the problem: threads for shared memory, message passing for clusters, GPUs for large regular data-parallel work, MapReduce style for big batch jobs.

    Agentic AI. A language-model agent plans, calls tools, observes results and repeats. Research questions: reliability over long chains, how to evaluate agents, safety (prompt injection, permissions), and applications to software engineering (code generation, repair, testing, review).

    Human-computer interaction and virtual reality. HCI studies how people use systems: heuristics for design, controlled experiments and usability studies for evaluation, quantitative models such as Fitts's law for pointing. VR adds constraints of latency, frame rate and comfort.

    This part covers software engineering, parallel computing, agentic AI, and human-computer interaction and virtual reality. Expect fundamentals plus questions that connect to practical experience.

    Q1. Explain the main software process models and when each fits.

    Answer. Waterfall: requirements, design, implementation, testing, maintenance in strict sequence; fits stable, well-understood requirements, but errors found late are costly. Iterative and agile (Scrum, XP): short cycles that deliver working increments with frequent feedback; fits changing requirements. Spiral: iterations driven by risk analysis. Continuous integration and delivery: every change is built and tested automatically.

    Q2. What is the difference between black-box and white-box testing? Give the levels of testing and a coverage example.

    Answer. Black-box tests check behaviour against the specification without looking at the code (equivalence classes, boundary values); white-box tests use the code structure (statement, branch, path coverage). Levels: unit, integration, system, acceptance; regression testing re-runs tests after changes.

    Example: for if (x>0x > 0x>0 && y>0y > 0y>0) {A} else {B}, statement coverage needs one input reaching A and one reaching B; branch coverage needs the condition true and false (the same two tests); condition coverage needs each of x>0x > 0x>0 and y>0y > 0y>0 to be both true and false, for example (1, 1), (1, -1), (-1, 1). Boundary-value example for an input range 1 to 100: test 0, 1, 2, 99, 100, 101.

    Q3. Explain SOLID principles and two design patterns with a use.

    Answer. Single responsibility (a class has one reason to change); open-closed (open to extension, closed to modification); Liskov substitution (a subtype can replace its base type without breaking behaviour); interface segregation (small, specific interfaces); dependency inversion (depend on abstractions, not concrete classes). Patterns: Observer (objects subscribe to be notified of changes, as in event handlers); Strategy (interchangeable algorithms behind one interface, such as different sorting or pricing rules); Singleton (one instance, with the risk of hidden global state); Factory (create objects without naming the concrete class).

    Q4. Parallel computing: define speedup, state Amdahl's law and compute an example.

    Answer. Speedup = time on one processor / time on p processors. Amdahl's law: if a fraction fff of the work is inherently serial, the speedup is at most 1f+1−fp\frac{1}{f + \frac{1 - f}{p}}f+p1−f​1​, and never more than 1f\frac{1}{f}f1​.

    Example: f=0.1f = 0.1f=0.1 and p=8p = 8p=8: 10.1+0.98=10.2125=4.7\frac{1}{0.1 + \frac{0.9}{8}} = \frac{1}{0.2125} = 4.70.1+80.9​1​=0.21251​=4.7; with unlimited processors the limit is 10. Gustafson's law instead scales the problem with ppp: speedup = ppp - fff (ppp - 1), more optimistic when larger problems are the goal. Sources of overhead: communication, synchronization, load imbalance, and contention.

    Q5. Explain a data race, a deadlock and how to avoid each in multithreaded code.

    Answer. A data race: two threads access the same variable at the same time, at least one writes, with no synchronization; example: two threads each run counter++ (read, add, write) and one update is lost. Fix with a mutex, an atomic operation, or by not sharing state. Deadlock: threads wait for each other in a cycle (see the four conditions and avoidance in section 1.2). Avoid it by acquiring locks in one global order. Also: false sharing (different variables on the same cache line making cores fight over it), and memory ordering (without barriers, one core may see writes in a different order than they were made).

    Q6. Compare shared-memory (threads, OpenMP), message-passing (MPI) and GPU programming.

    Answer. Shared memory: threads see the same memory; easy to share data, but needs locks and scales to one machine. MPI: separate processes exchange explicit messages; scales across machines, but the programmer manages data movement. GPU (CUDA): thousands of lightweight threads running the same code on different data (SIMD style); excellent for regular, data-parallel work such as matrix multiplication, poor for branching, irregular code, and when data transfer to the device dominates. MapReduce: a map step on independent pieces and a reduce step combining results; example word count: map emits (word, 1), reduce sums per word.

    Q6b. What is an LLM agent, and what are its main design problems?

    Answer. An agent is a loop around a language model: it receives a goal, decides on an action (call a tool, search, run code), observes the result, updates its context, and repeats until done. Components: the model, tools with typed interfaces, memory (the context window plus stored notes or retrieval), and a planner that breaks goals into steps. Problems: errors compound over long chains (if each step is 95% reliable, 20 steps succeed about 36% of the time); tool misuse and prompt injection (text read from the web can carry instructions); cost and latency; evaluating correctness (use test-based or checkable tasks); and safety (limit permissions, require approval for irreversible actions). Software-engineering uses: code generation and repair, test generation, log⁡\log log analysis, and requirements review.

    Q7. HCI and VR basics.

    Answer. Nielsen's usability heuristics include visibility of system status, match with the real world, user control and freedom, consistency, error prevention, recognition rather than recall, and flexibility. Fitts's law: the time to reach a target grows with log⁡2\log_2 log2​ of (distance / target width + 1), so big, close targets are quick to hit (which is why screen corners are easy targets). Evaluation methods: think-aloud usability tests, heuristic evaluation, AB\frac{A}{B}BA​ tests, and questionnaires such as the System Usability Scale. In VR, latency between head movement and the displayed image must stay roughly under 20 ms and frame rates high (90 Hz or more) to avoid motion sickness; locomotion by teleporting is more comfortable than smooth motion for many users.

    Q8. What would you ask about code quality metrics and technical debt?

    Answer. Cyclomatic complexity = number of decision points + 1 (edges - nodes + 2 for a control-flow graph with one connected component); high values mean many paths to test. Coupling (dependence between modules) should be low and cohesion (relatedness within a module) high. Technical debt is the cost of shortcuts that make future change slower; refactoring (changing structure without changing behaviour, protected by tests) pays it down.
